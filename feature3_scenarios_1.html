Feature 3 — Keep Size Context: scenario review

Size Filter V2 · prep doc for eng sync (Karen / Nikhil / Sharad / Anusha)

Agenda

  1. Goal: implement the PRD as originally written — auto-drop on category mismatch. (already the intended design, and Karen agreed to this in the last sync — not up for re-debate)
  2. Walk the scenarios below, confirm nothing breaks the auto-drop logic
  3. Decide the mechanics: how does the server correctly detect a fresh selection vs. a carried-over filter, without misfiring
  4. Assign owners for anything still open after this sync

Main issue

Goal: if the user is still browsing the same category after refining their query, keep the size filter applied — auto-drop it silently if the category no longer matches. This is the PRD as written.

Only open item: the server can't yet tell a filter the user just set apart from one carried over from an earlier query — so auto-drop risks clearing a selection the user made seconds ago.

Edge cases and open questions

Not a checklist to read aloud. Skim resolved rows for confirmation only, spend meeting time on open rows, and add anything new live as it comes up — that's what new is for.

#ScenarioWhy it mattersStatus
E1 User applies Select Size on query 1, smart-preview suggested a different category than what the user actually picked (e.g. query "nike" suggested shoes, user picks jackets instead) — no query 2 submitted yet. Must not trigger a mismatch check — no new query exists yet. Once "current filter category" is defined as whatever the user actually selected, this collapses into the same rule as S1–S5.
E2 The "fresh selection vs. carried-over filter" distinction — server can't currently tell these apart from the request shape alone. Needed before auto-drop can be safely implemented. Likely fix: client compares the new query text to the last query text it sent, and only tells the server to run mismatch evaluation when they differ.
E3 User keeps their explicitly-chosen filter (e.g. jackets, from E1), then submits a genuinely new query 2 with different category text (e.g. "nike pants"). Category mismatch (jackets ≠ pants) — evaluate same as S2, or exception because the filter was the user's own deliberate pick? Flagged as rare, never resolved.
E4 Filter is KEPT through query 2, then query 3 is submitted. Comparison basis undefined — does query 3 compare against the original filter category, or something else? Never discussed.
E5 Filter is DROPPED on mismatch, then a later query returns to the original category. Does the dropped filter auto-restore, or does the user reselect from scratch? Never discussed.
E6 User changes the category filter chip directly (not the query text) while a size filter is active. This is Fix 1's territory. Could it fire alongside a Feature 3 query-based check and conflict? Not addressed in either spec.
E7 Same query resubmitted verbatim, or pull-to-refresh. Should be a trivial match — worth confirming explicitly rather than assuming.
E8 Filter mode is My Size or All (not Select Size). Feature 3 shouldn't apply here — persistence is governed by Fix 1 instead. Worth confirming this boundary out loud.
E9 S1's KEEP depends on the FE recognizing "sneakers" and "shoes" as the same category (a synonym/taxonomy match), not just exact text match. This is a dependency on the existing V1 rule-based extractor's coverage — not something Feature 3's logic controls, but it directly affects how often real users actually get a KEEP. Worth flagging as a dependency, not a blocker.
E10 Mid-session, user manually reopens Select Size and switches the category themselves (e.g. shoes → bags) — no new query submitted, they just re-picked. Out of scope for Feature 3 itself, but whatever "current filter" tracking mechanism we decide for E2 needs to handle this gracefully — the baseline that later KEEP/DROP comparisons run against should update to the new pick.
